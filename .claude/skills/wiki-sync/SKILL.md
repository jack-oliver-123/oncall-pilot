# 同步 OpenSpec 变更到 WIKI

WIKI 是 OpenSpec artifact 的只读投影；同步器只生成文档页面和导航，不修改 OpenSpec 文件。

## 何时触发

- OpenSpec Change 新建、artifact 集合变化，或完成归档之后。
- 用户明确要求同步、重建、刷新 WIKI / 文档站导航。
- 验证或发布前需要确认 `docs/changes/` 与 OpenSpec 一致。

## 唯一入口

从仓库根目录执行：

```bash
python scripts/sync_wiki.py active <change-name>
python scripts/sync_wiki.py archive <change-name-or-archive-name>
python scripts/sync_wiki.py all
```

三种模式都会按当前 OpenSpec 状态重建并验证所有受管页面；`active` 和 `archive` 额外确认目标 Change 存在。

## 执行顺序

1. 创建、更新或归档 OpenSpec Change 后运行对应同步命令。
2. 同步器验证归档 delta specs：
   - `.openspec.yaml` 声明 `skip_specs: true` 且没有 delta specs 时直接通过。
   - 存在 delta specs 时，必须包含可解析 operation，且已同步到 main specs。
   - 空 operation、空 ADDED/MODIFIED/REMOVED、畸形 RENAMED 会失败；先修复 OpenSpec，不要跳过。
   - 真正未同步时先修复 OpenSpec 状态。
   - `--allow-unsynced` **仅**在用户针对**当前这一次**命令输出的完整错误列表与当前仓库状态作出一次性明确批准后使用；不得复用更早批准，不得在错误列表变化后沿用旧授权。
3. 确认命令输出的 include、目录、索引和导航验证均通过。
4. 运行 `npm run docs:build`，构建成功才算同步完成。

## 生成范围

- `docs/changes/active/<change>/index.md`
- `docs/changes/archive/<dated-change>/index.md`
- `docs/changes/index.md`
- `docs/.vitepress/config.mts`

生成页使用相对路径直接引用根级 `openspec/`，不要求 `docs/openspec` 符号链接，也不复制 artifact 内容。

## Guardrails

- 报错时停止并保留现有 OpenSpec 状态，不把失败报告为同步成功。
- 不手工编辑带 `Generated by scripts/sync_wiki.py` 标记的文件。
- 不把 WIKI 页面当作第二份规格或 Change 状态来源。
- 删除 stale 目录前，同步器必须确认目录带有受管生成标记。
- 独立校验与同步共用 OpenSpec 源期望；不要用已生成 frontmatter 回填日期来“修”校验。
